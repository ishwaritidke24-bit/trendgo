# TrendGo Backend Integration Plan

This document describes the current frontend architecture and the backend required to make TrendGo a personalized social event discovery platform. The current UI and mock data remain unchanged.

## Current Frontend Architecture

TrendGo is a React 19 application using Vite and TanStack Start. Routing is handled by TanStack React Router with generated route types. Tailwind CSS v4, CSS variables, Radix UI primitives, class-variance-authority, and Lucide icons provide the UI system.

The root route provides the document shell, global metadata, CSS, React Query provider, not-found handling, and an error boundary. The authenticated-looking pages share `AppShell`, which currently injects the hardcoded `CURRENT_USER` into the navbar. `QueryClient` is configured but no product queries or mutations exist yet.

Primary domain data is centralized in `src/data/mock.ts`. Most interactions use local React state, so state is lost on reload and is not shared between pages.

## Existing Pages and Routes

- `/` in `src/routes/index.tsx`: public landing page with hero discovery form, vibe categories, and trending event previews.
- `/home` in `src/routes/home.tsx`: personalized feed assembled from mock recommendations, social activity, popularity, and weekend filters.
- `/explore` in `src/routes/explore.tsx`: in-memory search, category/date/distance/price filters, sorting, and grid/list views.
- `/event/$eventId` in `src/routes/event/$eventId.tsx`: event detail, match reasons, attendee friends, organizer, actions, and similar experiences.
- `/friends` in `src/routes/friends.tsx`: friend activity, friend list, invitations, and social recommendations.
- `/events` in `src/routes/events.tsx`: Interested, Saved, Going, and Past event tabs.
- `/profile` in `src/routes/profile.tsx`: profile summary, interests, favorite categories, stats, and saved experiences.
- `src/routes/__root.tsx`: root document, providers, error boundary, and not-found page.

`src/routeTree.gen.ts` is generated by TanStack Router and should be regenerated by the router tooling after route changes rather than manually maintained.

These primitives are not backend-specific. They can remain in place while product-level pages receive API-backed data and mutations.

## Authentication-Related UI

There is currently no authentication implementation.

- `Navbar` supports an optional `user` and `onSignIn` callback and can render a `Get Started` button when signed out.
- `AppShell` always passes hardcoded `CURRENT_USER`, so current product pages appear authenticated.
- There are no login, signup, logout, password reset, onboarding submission, session provider, auth guard, access-token handling, or user-loading states.
- `profile.tsx` is a local profile display, not account management.

### Required future authentication flow

1. Public landing page offers sign in and sign up.
2. Client submits credentials to backend auth endpoints.
3. Backend hashes passwords and creates a secure session, preferably an HTTP-only, secure, same-site cookie.
4. Frontend loads `/api/auth/me` on startup and exposes the user through an auth provider or query.
5. Protected routes redirect unauthenticated users to `/login`.
6. Logout invalidates the server session and clears cached user-specific queries.
7. Profile and onboarding forms update the authenticated user through validated mutations.
8. Password reset should use short-lived, single-use tokens if it is included in the first auth release.

Use HTTP-only cookies instead of storing long-lived tokens in `localStorage`.

## Existing Forms and UI Flows

- `src/components/sections/hero.tsx` has controlled `what`, `where`, and `when` fields. Submit currently only prevents the default action; it does not search or navigate.
- `src/routes/explore.tsx` has a functional controlled search and filter experience, but all filtering runs against the local `EVENTS` array.
- `src/components/ui/form.tsx` provides React Hook Form integration, but no product form currently uses it.
- Zod and `@hookform/resolvers` are installed but no product validation schema or submitted backend form exists.
- Event Interested and Save controls in `event-card.tsx` use local component state.
- The event detail page has local Interested and Save state; Share, Invite friends, and organizer actions are presentational.
- Profile interest changes are local to the profile component.
- Many buttons are currently visual or no-op flows: location selection, notifications, Find friends, invite actions, Edit profile, Add interest, landing vibe actions, and Surprise Me.

## Existing Mock Data

`src/data/mock.ts` contains:

- `CATEGORIES` and the `Category` union.
- `Friend` interface and six hardcoded friends.
- `EventItem` interface and ten hardcoded Bengaluru events.
- `ActivityItem` interface and six social activity entries.
- `CURRENT_USER` with name, avatar, location, bio, interests, favorite categories, and stats.
- `MY_EVENTS`, a static map of event IDs grouped into interested, saved, going, and past.
- `eventById()` and `friendById()` in-memory lookup helpers.

Friend avatars use external `https://i.pravatar.cc` URLs. `trending-near-you.tsx` also has a separate hardcoded event preview type/data set, which should be consolidated with the main event model before production integration.

## State Management and Persistence

There is no global application state library.

Current state is local React state in the navbar, hero, event cards, event detail, explore filters, My Events tab selection, profile interests, and responsive UI primitives. React Context exists inside generic UI components but not for product state.

TanStack Query is installed and provided at the root, but there are no queries, mutations, loaders, or cache invalidation flows.

The application does not use `localStorage` or `sessionStorage` directly. The generic sidebar primitive writes a `sidebar_state` browser cookie. No event status, profile edits, auth state, filters, or onboarding data survive reloads.

## API and Service Files

There is no business API or service layer.

- `src/start.ts` configures TanStack Start middleware, including CSRF support for future server functions.
- `src/server.ts` is the SSR/server entry wrapper.
- `src/lib/error-capture.ts`, `error-page.ts`, and `lovable-error-reporting.ts` handle errors and preview/editor reporting.
- There is no `fetch` wrapper, Axios client, REST module, GraphQL client, database client, repository, or AI service.

The README mentions Express, MongoDB, REST APIs, and AI APIs, but those are not currently implemented or present in `package.json`.

## Required MongoDB Collections / Models

### `users`

- `_id`
- `email` with a unique index
- `passwordHash` or external auth provider ID
- `name`, `avatarUrl`, `bio`, `location`
- `interests`
- `favoriteCategories`
- `stats` or derived counters
- `createdAt`, `updatedAt`, `lastActiveAt`

Do not return `passwordHash` to the client.

### `events`

- `_id`
- `title`, `description`, `imageUrl`
- `category`, `tags`
- `startAt`, `endAt`, `timezone`
- `venue`, `area`, address fields, and GeoJSON location
- `price`, currency, capacity, status
- `organizerId`
- `createdAt`, `updatedAt`

Create a 2dsphere index for location-aware discovery and indexes for category, start time, price, and popularity.

### `organizers`

- `_id`
- `name`, `blurb`, `avatarUrl`, contact/public profile fields
- verification/status fields
- `createdAt`, `updatedAt`

### `eventStatuses`

One document per user/event relationship:

- `userId`
- `eventId`
- `status`: `interested`, `saved`, `going`, or `past` as an application-derived state
- `createdAt`, `updatedAt`

Use a unique compound index on `{ userId, eventId }`. Alternatively, maintain separate relationship collections if status history is required.

### `friendships`

- `requesterId`
- `recipientId`
- `status`: `pending`, `accepted`, `blocked`
- `createdAt`, `updatedAt`

Use a normalized pair or application rule to prevent duplicate reciprocal relationships.

### `eventActivity`

- `actorId`
- `eventId`
- `action`: interested, going, saved, attended
- `createdAt`

This supports the Friends feed and should be indexed by actor, event, and creation time.

### `invitations`

- `senderId`
- `recipientId`
- `eventId`
- `status`: pending, accepted, declined, expired
- `createdAt`, `respondedAt`

### `notifications`

- `userId`
- `type`
- `actorId`, `eventId`, invitation/friendship references
- `readAt`
- `createdAt`

### Optional later collections

- `recommendationSnapshots` for persisted recommendation explanations and experiments.
- `eventReviews` for post-event feedback.
- `searchEvents` only if a separate search engine is introduced.
- `sessions` if implementing database-backed sessions rather than a managed auth provider.

## Recommended REST API Endpoints

Use a consistent response envelope, cursor pagination for feeds, validation errors with field-level details, and authenticated user context from the session cookie.

### Authentication

- `POST /api/auth/signup`
- `POST /api/auth/login`
- `POST /api/auth/logout`
- `GET /api/auth/me`
- `POST /api/auth/refresh` if token-based auth is selected
- `POST /api/auth/forgot-password`
- `POST /api/auth/reset-password`

### Profile and onboarding

- `GET /api/me`
- `PATCH /api/me`
- `PATCH /api/me/interests`
- `PATCH /api/me/location`
- `GET /api/me/stats`

### Events and discovery

- `GET /api/events`
  - Query: `q`, `category`, `dateFrom`, `dateTo`, `distanceKm`, `priceMax`, `sort`, `lat`, `lng`, `cursor`, `limit`.
- `GET /api/events/:eventId`
- `GET /api/events/:eventId/similar`
- `GET /api/events/trending`
- `GET /api/feed`
- `GET /api/recommendations`
- `GET /api/recommendations/:eventId/reasons`

Recommendation responses should include the match percentage and explanation reasons currently shown by the UI.

### Event actions

- `PUT /api/events/:eventId/status` with `{ status: "interested" | "saved" | "going" }`
- `DELETE /api/events/:eventId/status/:status`
- `GET /api/me/events?status=interested|saved|going|past`
- `POST /api/events/:eventId/share` only if share analytics are needed
- `POST /api/events/:eventId/invitations`

### Friends and social activity

- `GET /api/friends`
- `GET /api/friends/search?q=`
- `POST /api/friends/:userId/request`
- `PATCH /api/friend-requests/:requestId`
- `DELETE /api/friends/:userId`
- `GET /api/social/activity`
- `GET /api/events/:eventId/attendees`

### Notifications

- `GET /api/notifications`
- `PATCH /api/notifications/:notificationId/read`
- `POST /api/notifications/read-all`

## Data Relationships

- A `User` creates or follows an `Organizer` through organizer ownership or organizer membership.
- An `Organizer` owns many `Events`.
- A `User` relates to many `Events` through `eventStatuses`.
- A `User` relates to many other users through `friendships`.
- A `User` creates `eventActivity` entries for event actions.
- `invitations` connect a sender, recipient, and event.
- `notifications` reference users, events, friendships, and invitations.
- Recommendations are derived from user interests, event tags/categories, distance, activity, friend activity, popularity, and recency.
- Match reasons should be generated from explainable signals rather than stored as arbitrary UI strings unless recommendation snapshots are introduced.

## Recommended Implementation Order

1. Define API contracts, error envelopes, domain types, and environment validation.
2. Create the MongoDB connection layer, indexes, models, seed data, and health endpoint.
3. Implement authentication and the `/api/auth/me` session flow.
4. Add user/profile and onboarding endpoints.
5. Add event and organizer APIs, then replace read-only mock data in Explore and event detail.
6. Add event status mutations and migrate Interested, Saved, Going, and Past.
7. Add the personalized home feed, match scores, and explainable recommendation reasons.
8. Add friendships, attendee queries, invitations, social activity, and notifications.
9. Replace landing-page hardcoded previews and connect hero/vibe discovery actions.
10. Add loading, empty, error, retry, optimistic-update, pagination, and authorization states.
11. Remove mock data only after API parity and end-to-end tests are in place.

## Proposed Architecture Summary

Use a server-owned MongoDB domain layer with HTTP-only session authentication and REST endpoints. Keep TanStack Router for page navigation and TanStack Query for server cache, request deduplication, mutations, optimistic updates, and invalidation. Model users, events, organizers, friendships, event statuses, activity, invitations, and notifications separately, with event status represented as a unique user/event relationship.

The first backend milestone should provide authenticated users, profile data, event search/detail, and event statuses. The next milestone should add recommendations and social activity. The frontend should continue using the existing UI components while replacing `src/data/mock.ts` reads with typed query hooks and replacing local action state with server mutations.
